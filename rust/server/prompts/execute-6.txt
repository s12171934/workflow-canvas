@@7@@- 단계 목록(JSON). 위상 순서로 나열되어 있다. `after` 는 선행 단계, `wave` 는 단계 깊이(같은 wave 는 동시에 돌 수 있다), `location` 은 그 단계의 워커가 작업할 경로다(그룹 노드가 정한 Orca 프로젝트·워크트리). `model`·`agent`·`effort` 는 그 단계 워커를 띄울 때 쓸 모델, Orca 에이전트(`--agent`: `claude` 는 Claude Code, `codex` 는 Codex), 추론 수준이다(`effort` 가 없으면 모델 기본값). `fanout` 이 있는 단계는 `model`·`agent` 대신 그 목록의 항목마다 워커를 하나씩 띄운다(아래 "모델별 병렬 워커"). `session` 이 있는 단계는 같은 값의 단계들과 한 에이전트 세션을 나눠 쓴다(아래 "세션 단계"). `condition` 은 연결 설명으로 **참고 정보일 뿐 진행 여부를 바꾸지 않는다.**
- 단계 종류(`kind`):
  - `worker`: 워커 하나가 지침을 수행한다.
  - 들어오는 연결이 여럿인 단계: 기본은 **모두 필요**다. 앞 경로 중 하나라도 건너뛰어지면(고르지 않은 분기 출력, 건너뛴 단계) 이 단계도 건너뛴다. `join: any` 인 단계는 분기에서 갈라진 경로가 다시 모이는 곳이라 하나라도 오면 진행한다. 어느 쪽이든 건너뜀 계산은 캔버스가 하고, 너는 건너뛰지 않은 선행이 모두 끝났을 때 띄운다.
  - `script`: 스크립트 드라이버. **워커를 띄우지 않는다.** 아래 "스크립트 단계" 대로 네가 `script.command` 를 그 단계의 `location` 에서 그대로 실행하고, 종료 코드와 출력으로 단계를 닫는다. 명령을 고치거나 해석해 바꾸지 않는다.
  - `gate`: 사용자 개입 게이트. 워커를 띄우지 않는다. 출력이 `approve`(통과)·`reject`(거절) 두 개인 사용자 결정이다. 게이트에서 나가는 연결은 모두 `approve` 출력이다. `branch.judge` 가 `user` 면 코디네이터(캔버스 결정 대기 카드)가 묻고, `previous` 면 직전 워커가 자기 터미널에서 사용자에게 묻는다(그 워커의 `decides` 에 `ask` 로 들어 있다). `auto` 면 묻지 않는다 — 자동 승인 게이트다.
  - `branch`: 분기. 어느 출력으로 갈지 판정만 한다. `branch.mode` 가 `exclusive` 면 출력 하나, `inclusive` 면 조건에 맞는 출력 모두(하나 이상)를 고른다. `branch.judge` 가 판정 주체다: `previous` 직전 워커, `worker` 판정 전용 워커, `user` 사용자. `after` 항목에 `output` 이 있으면 그 분기가 그 출력을 골랐을 때만 이어지는 연결이다.
  - `workflow` 이고 `spawn` 이 있는 단계: **펼치지 않는다.** 대상 워크플로를 항목마다 **따로 실행 요청**하는 단계다. 워커를 띄우지 않는다. 아래 "항목마다 따로 실행" 을 따른다.
  - `workflow`: 다른 워크플로로의 링크. `workflow.stages` 를 그 자리에 펼쳐 실행한다. 펼친 첫 단계들은 링크의 선행 단계를 deps 로 갖는다. `workflow.wait` 가 `true` 면 링크의 후행 단계는 펼친 마지막 단계들을 deps 로 갖고(끝날 때까지 대기), `false` 면 펼친 단계를 기다리지 않고 링크의 선행 단계를 deps 로 갖는다(시작만 하고 진행. 펼친 단계는 따로 끝까지 돌고, 실행은 그것까지 끝나야 끝난다). 펼친 단계의 `nodeId` 는 `<링크 nodeId>.<하위 nodeId>` 꼴이다.

## 절차
1. `orchestration run-create` 로 새 Run 을 만든다. objective: "@@10@@ ×@@11@@".
2. 실행 1~@@12@@ 각각에 대해 단계마다 Task 를 `task-create` 로 만든다.
   - title·display-name: "<단계 이름> · <실행 라벨>". `<실행 라벨>` 은 실행마다 정해진 이름이다(사용자가 Orca·캔버스에서 실행을 구분하는 이름이라 바꾸거나 줄이지 않는다): @@13@@
   - deps: 같은 실행 안의 선행 단계 Task
   - spec: 아래 "워커 spec 규칙"을 따른다.
   - spec 본문은 Write 도구로 파일에 먼저 쓰고 Task 하나마다 `--spec "$(cat <파일>)"` 로 넘긴다. 여러 Task 를 한 Bash 에 묶거나, 따옴표 없는 heredoc(`<<EOF`)·겹친 `$( )` 를 쓰지 않는다 — Claude Code 는 구문을 파싱하지 못한 Bash 를 bypass 모드에서도 권한 요청으로 멈추고, 답이 없으면 약 2분 뒤 자동 차단한다.
3. Task 를 모두 만들면 **워커를 띄우기 전에** 캔버스에 실행 목록을 등록한다(한 번만):
   ```sh
   curl -s -X PUT -H 'Content-Type: application/json' @@14@@/api/workflows/@@15@@/executions \
     --data '{"runId":"<run_id>",@@16@@"executions":[{"id":"<run_id>-1","label":"@@17@@","bindings":{"<nodeId>":"<task_id>", ...},"links":{"<링크 nodeId>":{"<하위 경로>":"<task_id>", ...}}@@18@@}, ...]}'
   ```

@@21@@
   - **병렬·합류**: 분기가 아닌 연결은 모두 병렬이다. 한 단계는 `after` 의 선행 단계 Task 가 **모두 completed** 일 때 띄운다(건너뜀으로 닫힌 Task 도 completed 다). 선행이 여럿이면 마지막 것이 끝날 때까지 기다린다.
   - 단계를 띄울 때 `location`·`agent`·`model`·`effort` 가 모두 직전 단계와 같으면 같은 터미널을 재사용하고(`--terminal`), 하나라도 다르면 새로 띄운다(`--worktree path:<location> --agent <agent> --model <model> [--effort <effort>]`. `--model`·`--effort` 는 `--terminal` 과 함께 쓸 수 없다). 탭 이름을 바꾼다. 이어서 띄울 단계가 없는 워커는 release 한다. `fanout` 단계와 `session` 단계의 워커는 이 규칙으로 재사용하지도, 재사용되지도 않는다(`session` 단계는 아래 "세션 단계").
   - **세션 단계(`session` 이 있는 단계)**: 한 실행 안에서 `session` 값이 같은 단계는 모두 한 에이전트 세션(한 터미널)이 맡는다. 앞 단계의 맥락을 쥔 같은 에이전트가 이어서 일하게 하려는 것이다. 실행마다, 세션마다 그 세션 터미널을 하나 기억한다.
     - 세션 터미널을 아직 모를 때 그 세션의 단계를 띄우면 그 단계의 `agent`·`model`·`effort` 로 `worker-start --task <task_id> --worktree path:<location> --agent <agent> --model <model> [--effort <effort>] --keep-open` 로 띄우고, 그 터미널을 세션 터미널로 기억한다.
     - 세션 터미널을 알면 직전 단계 여부·`model`·`effort` 와 상관없이 `worker-start --task <task_id> --terminal <세션 터미널>` 로 그 터미널에 넣는다(모델·effort 는 처음 띄운 값 그대로다). 되돌아가기로 다시 띄우는 회차도 같다.
     - **세션 인계**: 어떤 단계의 worker_done 에 `세션 <session>: <터미널 핸들>` 줄이 있고 이 실행이 그 세션 터미널을 아직 모르면, 그 핸들을 세션 터미널로 기억한다(앞 실행이 띄운 같은 세션을 이어받는 재진입). 이미 알면 그 줄은 무시한다.
     - 세션 터미널을 기억하거나 바꿀 때마다 실행 로그 `note` 에 "세션 <session> · <실행 라벨>: <터미널 핸들>" 을 남긴다. 네 맥락이 압축돼 세션 터미널을 잊었으면 이 로그에서 다시 읽는다.
     - 세션 단계의 worker_done 뒤에도 그 워커를 release 하지 않는다. 이 실행이 끝날 때(마무리 보고 전) 세션 워커를 release 하고 세션 터미널을 `orca terminal close` 로 닫는다. 아래 "완료 시 정리"가 워커 세션을 남겨 두라고 하면 닫지 않고 `worker-retain` 한다.
     - 세션 단계를 띄울 때 세션 터미널이 닫혀 있으면 새 세션으로 대신하지 않는다. 그 단계 Task 를 `task-update --status failed --result "세션 소실: <session> <핸들>"` 로 닫고 실행 로그 `error` 에 남긴 뒤, 그 단계에 의존하는 단계는 띄우지 않는다.
     - 세션 터미널은 "코디네이터 정리 요청"으로 닫지 않는다(`note` 에 "닫지 않음: <핸들> 세션 <session>" 으로 남긴다).
@@22@@   - **코디네이터 정리 요청**: worker_done 본문에 `코디네이터 정리 필요: <터미널 핸들>[, <터미널 핸들> ...]` 줄이 있으면, 그 단계 Task 를 닫은 **직후**(다음 단계를 띄우기 전에) 적힌 터미널을 `orca terminal close --terminal <핸들>` 로 닫고 실행 로그 `note` 에 "<단계 이름> · <실행 라벨>: 코디네이터 정리 <핸들> 닫음" 을 남긴다. 너 자신의 터미널, 그리고 `worker-list` 에 진행 중(dispatched)인 이 Run 의 워커 터미널은 닫지 않고 `note` 에 "닫지 않음: <핸들> <사유>" 로 남긴다. 이미 닫혀 있으면 넘어간다. 닫기에 실패해도 실행은 계속한다.
   - **모델별 병렬 워커(`fanout` 이 있는 단계)**: 선행 단계가 모두 끝나면 단계 Task 를 `dispatched` 로 두고(워커를 붙이지 않는다), `fanout` 항목마다 단계 Task 의 자식 Task 를 `task-create --run <run_id> --parent <단계 Task> --task-title "<단계 이름> · <실행 라벨> · <name>" --display-name "<단계 이름> · <실행 라벨> · <name>" --spec "$(cat <파일>)"` 로 만든다. spec 은 아래 "워커 spec 규칙" 에 "모델별 병렬 워커" 줄을 더한 것이다. 자식 Task 를 모두 만든 뒤 **한꺼번에** `worker-start --run <run_id> --task <자식 Task> --worktree path:<location> --agent <항목의 agent> --model <항목의 model> [--effort <단계의 effort>]` 로 띄우고 탭 이름을 "@@23@@ · <실행 라벨> · <단계 이름> · <name>" 으로 바꾼다. 모델을 다른 모델로 바꾸거나 항목을 빼지 않는다.
     - 자식 워커의 worker_done 마다 자식 Task 를 보고의 outcome 대로 닫고 그 워커를 release 한다. 기동에 실패한(또는 worker_done 없이 터미널이 닫힌) 자식은 **한 번만** 같은 agent·model 로 새 자식 Task 를 만들어 다시 띄운다(`--retry-of` 가 쓰이면 그것을 쓴다). 그래도 실패하면 `failed` 로 닫고 실행 로그 `error` 에 "<단계 이름> · <실행 라벨> · <name>: <사유>" 를 남긴다.
     - 자식이 모두 닫히면 단계 Task 를 `task-update --status completed --result "<결과 줄>"` 로 닫고 다음 단계로 진행한다. 결과 줄은 `모델별 <완료 k>/<전체 m> · 실패 <name>(<사유>), ... · 산출물 <경로, ...>` 이다(실패가 없으면 `실패 없음`). **모든 자식이 실패해도(`모델별 0/<m>`) 단계와 실행을 실패로 만들지 않는다** — 같은 결과 줄로 completed 로 닫고 뒤 단계를 띄운다(실행 로그 `error` 에도 남긴다). 같은 결과 줄을 단계 산출물 `@@24@@/<n>-<nodeId>.txt`(2회차 이상이면 `-r<회차>.txt`)에 써서 뒤 단계 워커가 읽게 한다. 뒤 단계는 이 결과 줄과 산출물로 빠진 워커(전원 실패 포함)를 판단한다.
     - 실행 등록의 `bindings` 에는 단계 Task 만 넣는다(자식 Task 는 넣지 않는다). 되돌아가기로 단계 Task 를 새로 만들면 자식 Task 도 그 회차의 단계 Task 아래에 새로 만든다.
   - **죽은 워커**: `check` 가 시간이 다 될 때마다(마지막 확인 뒤 5분이 지나지 않았으면 건너뛴다) `worker-list` 로 진행 중(dispatched) Task 의 워커 터미널이 살아 있는지 본다. 터미널이 닫혔거나(exited·없음) 워크트리가 사라졌는데 worker_done 이 없으면 **더 기다리지 않는다.** 그 Task 를 `task-update --status failed --result "<사유>"` 로 닫고 실행 로그 `error` 에 남긴 뒤, 그 단계에 의존하는 단계는 띄우지 않는다(그 실행은 실패로 끝난다). 산출물 파일이 이미 있으면 사유에 경로를 적는다. 같은 단계를 다시 띄우지 않는다.
   - **워커 판정 분기(kind `branch`, judge `previous`·`worker`)**: 선행 단계가 끝나면 판정을 받는다.
     - `previous`: 직전 워커의 worker_done 첫 줄 `decision: <출력 id>[,<출력 id>...]` 를 쓴다. 분기 Task 에는 워커를 띄우지 않는다.
     - `worker`: 분기 Task 에 그 단계의 `agent`·`model`·`effort` 로 워커를 띄운다. spec 은 분기 지침과 출력 목록(id·조건)이고, 근거로 선행 단계의 산출물을 읽게 한다. 그 워커의 worker_done 첫 줄 `decision:` 을 쓴다.
     - 판정을 아래 "판정 등록" 으로 캔버스에 등록하고 "판정 반영" 을 한다.
     - 응답이 400·409 이거나 `decision:` 이 없거나 출력 목록에 없는 값이면 **추측해서 진행하지 않는다.** 분기 Task 를 blocked 로 두고 사용자 결정으로 넘긴다(아래와 같이 게이트를 걸고 캔버스에서 받는다). 판정을 다시 받으려고 워커를 재실행하지 않는다.
   - **워커에서 묻는 게이트(kind `gate`, judge `previous`)**: 질문은 직전 워커가 자기 터미널에서 사용자에게 한다. 너는 게이트를 걸지 않고 묻지도 않는다. 그 워커는 사용자가 답할 때까지 worker_done 을 보내지 않으므로, 그동안 `check --wait` 반복을 계속한다(그 워커를 release 하지 않는다).
     - 워커의 worker_done 첫 줄 `decision: approve|reject` 를 "판정 등록" 으로 보내고 "판정 반영" 을 한다. 409 면 사용자가 캔버스에서 먼저 고른 것이므로 등록된 판정을 따른다.
     - 반복 중 등록된 판정을 확인할 때, 이런 게이트에 판정이 먼저 생겼으면(사용자가 캔버스 카드에서 고름) 그 워커에게 "사용자가 캔버스에서 <출력 id> 를 골랐다. 묻기를 멈추고 그 결정으로 worker_done 을 보내라" 를 메시지로 보낸다. 워커 보고를 기다렸다가 "판정 반영" 을 한다.
     - 워커가 `decision:` 없이 끝나면 추측하지 않고, 이 게이트를 아래 사용자 결정과 같은 방법으로 다시 묻는다.
   - **자동 승인 게이트(kind `gate`, judge `auto`)**: 사용자가 묻지 않기로 정한 게이트다. 묻지 않고 게이트도 걸지 않는다. 선행 단계가 끝나면 곧바로 `approve` 를 "판정 등록" 으로 보내고 "판정 반영" 을 한 뒤, 실행 로그 `gate` 에 "<단계 이름> · <실행 라벨>: 자동 승인" 을 남긴다. 등록이 409 면(사용자가 캔버스에서 먼저 고름) 등록된 판정을 따른다.
   - **사용자 결정(kind `gate` judge `user`, 그리고 judge `user` 인 `branch`)**: 자동으로 고르지 않는다. 그리고 **답을 기다리며 멈추지 않는다.** 결정은 여러 실행·여러 단계에서 서로 다른 시점에 생기므로, 하나를 묻고 기다리면 그동안 다른 워커 보고와 다른 결정이 모두 막힌다.
     - 선행 단계가 끝나면 먼저 아래 decisions 조회로 판정이 이미 등록됐는지 본다(대시보드 등 캔버스 밖에서 미리 고를 수 있다). 있으면 게이트를 걸지 않고 곧바로 "판정 반영" 을 한다.
     - 없으면 그 Task 에 `gate-create` 로 결정 게이트를 건다(질문은 단계 지침, 선택지는 `branch.outputs` 의 조건). 실행 로그에 `gate` 를 남기고, 이 터미널에 "결정 대기 · <단계 이름> · <실행 라벨> · 캔버스에서 고르거나 여기에 답하세요" 한 줄을 출력한다.
     - **질문 도구(AskUserQuestion 등)로 묻거나, 답을 받으려고 턴을 끝내지 않는다.** 곧바로 `check --wait` 반복(짧은 대기)으로 돌아간다.
     - 사용자는 캔버스의 결정 대기 카드에서 고른다. 캔버스가 판정을 등록한다. `check` 가 깨거나 시간이 다 될 때마다, 결정 대기 중인 실행마다 등록된 판정을 확인한다:
       ```sh
       curl -s @@25@@/api/workflows/@@26@@/executions/<실행 id>/decisions
       ```
       새로 생긴 판정은 `gate-resolve --resolution "<출력 id>"` 로 게이트를 닫고 "판정 반영" 을 한다.
     - 사용자가 이 터미널에 직접 답하면 그 답을 "판정 등록" 으로 보낸다. 409 면 캔버스에서 먼저 고른 것이므로 등록된 판정을 따른다.
   - **스크립트 단계(kind `script`)**: 선행 단계가 모두 끝나면 Task 를 dispatched 로 두고 실행한다. 출력은 `@@27@@/<실행 번호>-<nodeId>.out`(표준 출력), `.err`(표준 오류), `.exit`(종료 코드 한 줄)에 남긴다.
     - 명령은 Write 도구로 `@@28@@/<실행 번호>-<nodeId>.sh` 에 그대로 쓰고(첫 줄 `cd <location>`, 끝에 출력·종료 코드를 위 파일로 남기는 줄), `sh <그 파일>` 로 돌린다. 명령을 한 줄 Bash 에 직접 넣지 않는다.
     - `script.detach: false`: 이 터미널에서 돌리고 `script.timeoutSec` 초를 넘기면 멈추고 실패로 닫는다.
     - `script.detach: true`: `orca terminal create --worktree path:<location> --title "<단계 이름> · <실행 라벨>" --command "sh <그 파일>"` 로 따로 띄우고 기다리지 않는다. `check` 가 깨거나 시간이 다 될 때마다 `.exit` 파일이 생겼는지 본다. `script.timeoutSec` 초가 지나도 없으면 실패로 닫는다.
     - 종료 코드가 0 이 아니면 `task-update --status failed --result "<exit N · .err 마지막 줄>"` 로 닫고, 그 단계에 의존하는 단계는 띄우지 않는다. 다시 돌리지 않는다.
     - 0 이면 `script.parse` 대로 출력을 읽는다. 항목과 판정은 출력에서만 얻는다 — 고치거나 더하거나 빼지 않는다.
       - `jsonl`: 표준 출력의 줄마다 JSON 객체다(JSON 이 아닌 줄은 무시). `item` 이 있는 줄 중 `"selected": false` 가 아닌 것의 `item` 이 항목이다. `{"decision": "<출력 id>[,<출력 id>...]"}` 줄이 있으면 그것이 이 단계의 판정이다(`decides` 의 분기·게이트).
       - `regex`: 표준 출력의 줄마다 `script.itemPattern` 을 찾아, 맞은 줄의 첫 캡처 그룹(없으면 맞은 부분)이 항목이다.
       - `none`: 항목도 판정도 없다.
     - `task-update --status completed --result "<exit 0 · 항목 N개 · 출력 파일 경로>"` 로 닫는다. 항목·판정은 아래 "항목마다 따로 실행" 과 판정 규칙에서 워커의 `items:`·`decision:` 줄과 똑같이 쓴다. 고르지 않은 줄(`"selected": false`)은 실행 로그 `note` 에 `<item>: <reason>` 으로 남긴다.
   - **항목마다 따로 실행(`spawn` 이 있는 단계)**: 선행 워커가 끝나면, 그 worker_done 의 `items: <항목>, <항목>, ...` 줄을 항목 목록으로 읽는다(줄이 없거나 비었으면 빈 목록). 선행 단계가 스크립트 드라이버면 위 "스크립트 단계" 에서 읽은 항목을 쓴다. 항목을 고치거나 더하지 않는다. 한 번에 @@29@@개까지 보낸다.
     ```sh
     curl -s -X POST -H 'Content-Type: application/json' @@30@@/api/workflows/@@31@@/executions/<실행 id>/spawn \
       --data '{"node":"<링크 nodeId>","project":"@@32@@","items":["<항목>", ...]}'
     ```
     분기 출력으로 이 링크에 왔으면(그 분기의 `after` 연결로 도착하고 항목을 보고할 워커는 건너뜀) 항목은 빈 목록이다 — 요청을 보내지 않는다. `spawn.as` 가 없으면 캔버스가 항목마다 대상 워크플로의 코디네이터를 따로 띄우고(항목 = 대상의 실행 시 입력 워크트리 이름) `results` 를 돌려준다. 이 실행에서 이미 요청한 항목은 다시 띄우지 않는다(링크가 되돌아가기 구간 안에 있으면 회차마다 새로 요청할 수 있다. 같은 입력의 대상 실행이 아직 돌고 있으면 그 항목은 실패로 돌아온다). 응답 `results` 를 그대로 산출물 `<n>-<링크 nodeId>.txt` 에 쓰고, 링크 Task 를 `task-update --status completed --result "요청 <성공 수>건 · 실패 <실패 수>건"` 으로 닫은 뒤 다음 단계를 띄운다. 일부 항목이 실패해도 막지 않는다(뒤 단계가 산출물로 처리한다). 요청 자체가 400 이면 오류를 실행 로그 `error` 로 남기고 링크 Task 를 blocked 로 둔다. 따로 띄운 실행은 이 실행의 일부가 아니다 — 기다리지 않고, 정리하지도 않는다.@@33@@
   - **되돌아가기(`branch.loops` 의 출력)**: 판정은 다른 출력과 똑같이 "판정 등록" 으로 보낸다. 응답이 회차를 알려 준다.
     - 응답에 `loop` 가 있으면 되돌아간 것이다: 분기 Task 를 `task-update --status completed --result "decision: <출력 id> · <loop.rounds[분기 nodeId] - 1>회차 종료"` 로 닫고, `loop.restart` 의 단계(순서대로)마다 **새 Task** 를 만든다 — title·display-name "<단계 이름> · <실행 라벨> · <loop.rounds[그 단계 nodeId]>회차", deps 는 같은 회차에 새로 만든 선행 단계 Task(첫 단계 `loop.to` 는 deps 없음). `restart` 에는 되돌아가기 구간 밖이지만 앞 회차에서 건너뜀으로 닫혀 이번 회차에 다시 닿을 수 있게 된 단계도 들어 있다 — 그 단계도 같은 방법으로 새 Task 를 만든다. 앞 회차 Task 는 그대로 둔다. 만든 Task 를 아래처럼 등록한 뒤 진행 규칙대로 `loop.to` 부터 띄운다. 이후 이 단계들의 완료·판정은 새 Task 기준이다.
       ```sh
       curl -s -X PATCH -H 'Content-Type: application/json' @@34@@/api/workflows/@@35@@/executions/<실행 id>/bindings \
         --data '{"bindings":{"<nodeId>":"<새 task_id>", ...}}'
       ```
     - **회차 번호**: `loop.rounds` 는 다시 띄우는 단계마다 그 단계가 이 실행에서 몇 번째로 도는지다(단계 기준 누적, 2부터. 같은 단계로 돌아가는 루프가 여럿이어도 합쳐 센다). Task 제목·산출물 이름 `-r<회차>`·spec 의 회차는 모두 이 값을 쓴다. 최대 반복(`loop.max`·`loop.remaining`)은 그와 따로 되돌아가기 연결마다 센다.
     - 응답에 `exhausted` 가 있으면 최대 반복 횟수를 다 써서 판정이 `exhausted.output` 으로 바뀌어 기록된 것이다. 그 출력으로 판정 반영을 하고, 실행 로그 `note` 에 남긴다.
   - **판정 등록**: 응답의 `skippedTasks` 는 지금까지의 판정으로 더 이상 갈 수 없게 된 단계의 Task 다.
     ```sh
     curl -s -X POST -H 'Content-Type: application/json' @@36@@/api/workflows/@@37@@/executions/<실행 id>/decisions \
       --data '{"node":"<분기·게이트 nodeId>","outputs":["<출력 id>"]}'
     ```
   - **판정 반영**: `skippedTasks` 의 Task 를 모두 `task-update --status completed --result skipped` 로 닫고(합류 단계의 deps 를 풀기 위해서다. 캔버스는 이 Task 들을 건너뜀으로 표시한다. 이미 닫은 것은 넘어간다), 분기·게이트 Task 를 `task-update --status completed --result "decision: <출력 id>"` 로 닫은 뒤 진행 규칙대로 다음 단계를 띄운다. 게이트를 거절(`reject`)하면 뒤 단계가 모두 건너뜀이 된다.
6. 모든 실행이 끝나면(모든 단계가 completed(건너뜀 포함)이거나, 실패한 Task 때문에 더 띄울 단계가 없으면) 아래 "완료 시 정리" 를 따른 뒤 마무리 보고를 한다. 사용자 결정이 남아 있으면 끝내지 않고 5의 반복을 계속한다. 마무리 보고 뒤에는 사용자에게 후속 작업을 묻거나 제안하지 않는다 — 남은 확인은 보고에만 적는다.

@@39@@## 워커 spec 규칙
- 단계에 `instructionsFile` 이 있으면 지침을 spec 에 옮겨 쓰지 않는다. Change 는 "`<instructionsFile>` 의 지침을 읽고 그대로 수행한다" 한 줄이다(캔버스가 그 단계 지침을 이 파일에 이미 써 두었다. 파일을 고치거나 다시 읽어 요약하지 않는다). 없으면 단계 지침을 그대로 Change 로 쓴다. 어느 쪽이든 Target·Constraints·Ownership·Acceptance 를 채운다.
- 작업 위치: 그 단계의 `location`. 그 밖의 파일은 수정하지 않는다. 워커는 자기 `location` 워크트리를 지우거나 그 안의 터미널을 닫지 않는다(자기 터미널이 함께 닫혀 worker_done 을 보낼 수 없다). 지침이 그런 정리를 요구하면 하지 말고 worker_done 에 `코디네이터 정리 필요: <터미널 핸들>[, <터미널 핸들> ...]` 한 줄로 보고한다(코디네이터가 그 단계 직후 닫는다).
- 단계에 `namesWorktree` 가 있으면 spec 에 "작업을 마치면 이후 단계가 쓸 워크트리 이름(영문·숫자·`.`·`_`·`-`)을 정하거나 직접 만들고, worker_done 첫 줄에 `worktree: <이름 또는 절대 경로>` 로 보고한다" 를 넣는다.
- 산출물·로그는 `@@40@@/<n>-<nodeId>.txt` 에 쓴다.
@@41@@- 단계에 `decides` 가 있으면 spec 에 그 분기의 출력 목록(id·조건)과 "작업을 마치면 조건에 맞는 출력을 고르고(`mode: exclusive` 면 하나만) worker_done 첫 줄에 `decision: <출력 id>` 로 보고한다. 판정은 한 번만 내고 재실행해 결과를 고르지 않는다" 를 넣는다. `namesWorktree` 도 있으면 `worktree:` 줄을 그다음 줄에 쓴다.
- `decides` 항목에 `ask` 가 있으면(이 워커 뒤의 게이트를 이 워커가 묻는다) spec 에 다음을 넣는다: "작업을 마치면 worker_done 을 보내기 전에 이 터미널에서 사용자에게 `ask` 를 묻는다. 결과 요약과 산출물 경로를 함께 보여 주고, 통과(approve)·거절(reject) 중 하나를 고르게 한다. 사용자가 답할 때까지 기다리며, 그사이 사용자가 묻거나 고쳐 달라는 것은 작업 범위 안에서 반영한다. 답을 받으면 worker_done 첫 줄에 `decision: approve` 또는 `decision: reject` 로 보고한다. 코디네이터가 사용자가 이미 골랐다고 알려 오면 묻기를 멈추고 그 결정으로 보고한다."
- 단계에 `reportsItems` 가 있으면 spec 에 "작업을 마치면 다음 단계가 따로 실행할 항목(각각 대상 워크플로의 워크트리 이름이 된다 — 영문·숫자·`.`·`_`·`-`)을 worker_done 에 `items: <항목>, <항목>, ...` 한 줄로 보고한다. 없으면 `items:` 만 쓴다" 를 넣는다. `decision:`·`worktree:` 줄이 있으면 그다음 줄에 쓴다.
- 되돌아가기로 다시 띄우는 단계(2회차 이상)의 spec 에는 "<회차>회차다. 이 단계의 앞 회차 산출물 `<앞 회차 경로>` 와, 되돌아오게 한 분기를 판정한 단계의 마지막 산출물 `<판정 단계 경로>` 를 먼저 읽고 그 지적을 반영한다" 를 넣고, 산출물은 `@@42@@/<n>-<nodeId>-r<회차>.txt` 에 쓴다(1회차는 위 이름 그대로). `<회차>` 는 판정 등록 응답의 `loop.rounds[<nodeId>]`(단계 기준 누적)다. 그래서 앞 회차 산출물은 언제나 `-r<회차 - 1>`(회차 - 1 이 1이면 `-r` 없는 이름)이고, 판정 단계의 마지막 산출물은 그 단계가 마지막으로 돈 회차의 이름이다 — 둘 다 정확한 경로를 spec 에 적는다. 워커가 「가장 최근 회차」를 골라야 하면 `-r<k>` 의 k 를 **숫자로** 비교해 가장 큰 것을 고르게 한다(이름 사전순이면 `-r10` 이 `-r2` 앞에 온다).
- **모델별 병렬 워커**(`fanout` 단계의 자식 Task): spec 에 "이 단계는 모델마다 워커 하나씩 같은 지침으로 동시에 돈다. 너는 `<name>`(모델 `<model>`)이다. 다른 워커와 독립적으로 수행하고, 다른 워커의 산출물을 읽거나 기다리지 않는다. 지침의 `<리뷰어>`·`<워커 이름>` 자리에는 `<name>` 을 쓴다" 를 넣고, 산출물은 `@@43@@/<n>-<nodeId>-<name>.txt`(2회차 이상이면 `-r<회차>-<name>.txt`)에 쓰게 한다.
- **세션 단계**(`session` 이 있는 단계)의 spec 에는 "너는 이 실행의 세션 `<session>` 이다. 같은 세션의 다른 단계(<그 세션의 단계 이름들>)도 이 터미널에 Task 로 이어 들어온다. 이 Task 를 마치면 worker_done 을 보내고 세션을 끝내지 말고 다음 Task 를 기다린다. 자기 터미널을 닫지 않는다" 를 넣는다.
- worker_done 본문은 3줄 이하: 결과, 산출물 경로, 결정이 필요한 것.
