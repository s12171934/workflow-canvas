> Orca CLI와 연결하는 로컬 그래프 캔버스다. 워크플로를 편집하고, Orca Run의 Task 의존 관계를 가져와 각 단계의 실제 실행 상태를 관찰한다.

## 기능

- 노드 종류 — 두 계열이다.
  - 그룹 노드 — 대상은 Orca에 열린 프로젝트 또는 워크트리. 단계를 그룹 안에 끌어 놓으면 들어가고 밖으로 끌어내면 빠진다. 프로젝트 그룹은 중첩하지 않고, 워크트리 그룹은 프로젝트·워크트리 그룹 안에 넣을 수 있다(워크트리 안의 워크트리는 Orca에서 하위 워크트리로 만든다, 최대 4단계). 그룹을 지우면 안의 것은 한 단계 위로 옮겨진다.
  - 워크트리 규칙 — 기존 선택은 고를 때 이름·브랜치를 기록해, 실행 때 없으면 같은 이름으로 다시 만든다. 새로 생성은 이름을 직접 지정·이전 단계 에이전트가 결정(이름 보고 또는 직접 생성)·실행 시 입력 중에서 고른다. 같은 이름·브랜치의 워크트리가 이미 있으면 재사용하고, 병렬 실행 중에도 같은 이름은 한 번만 만든다. 「실행마다 따로 만들기」를 켜면 이름 뒤에 실행 번호를 붙인다. 다른 워크트리 그룹 안에 있지 않은 새 워크트리는 「부모 워크트리」(절대 경로 또는 `{{설정값}}`)를 주면 그 워크트리의 하위로 만들고, 비우거나 설정값이 비면 부모 없이 만든다.
  - 일반 노드 — 워커, 사용자 개입 게이트, 분기, 워크플로 링크(저장된 다른 워크플로를 그 자리에 펼쳐 실행), 메모(실행과 무관).
  - 메모 그룹 — 노드를 묶어 보여 주기만 하는 크기 조절 상자. 옮기면 안에 든 노드(중심이 안에 있는 단계, 통째로 들어간 그룹)가 함께 움직인다. 프로젝트·워크트리 그룹 안에도 넣을 수 있다(끌어 넣으면 들어가고 그룹과 함께 움직인다). 실행·작업 위치와 무관하고, 메모 그룹 안에 다른 노드를 소속시키거나 연결할 수 없으며, 지워도 안의 노드는 남는다.
- 모델·추론 수준 — 워커와 판정 전용 워커를 쓰는 분기는 노드마다 모델과 effort(`low`·`medium`·`high`·`xhigh`·`max`)를 고를 수 있다. 비워 두면 기본값(모델 `claude-opus-5-5`, effort 는 모델 기본)을 쓴다. 코디네이터는 단계마다 그 값으로 `worker-start --model … [--effort …]` 를 부르고, 위치·모델·effort 가 모두 직전 단계와 같을 때만 터미널을 이어 쓴다.
- 세션 — 워커 단계에 같은 `session` 이름을 주면 한 실행 안에서 그 단계들을 한 에이전트 세션(한 터미널)이 이어서 맡는다. 코디네이터는 처음 닿는 단계를 `worker-start … --keep-open` 으로 띄우고, 나머지는 `worker-start --task … --terminal <세션 터미널>` 로 같은 터미널에 넣는다. 세션 에이전트는 매번 코디네이터의 워커로 Task 를 받으므로 Orca·대시보드에서 코디네이터 아래에 보인다. 앞 실행의 세션을 이어받을 때는 단계 워커가 worker_done 에 `세션 <이름>: <터미널 핸들>` 줄을 적는다(세션 인계).
- 자연어 생성 — Orca가 Claude 에이전트를 띄워 만든다(캔버스는 모델을 직접 부르지 않는다). 사이드바·빈 캔버스의 「자연어로 만들기」는 요청과 고른 프로젝트를 읽고 단계·연결·지침·분기·게이트를 만든 새 워크플로를 저장해 연다(그룹은 만들지 않는다). 단계 속성의 「자연어로 지침 생성」은 앞뒤 단계와 프로젝트 코드를 읽고 그 단계의 지침(필요하면 이름)을 써서 반영한다. 에이전트는 결과를 캔버스 API로 보내고, 서버가 검증해 틀리면 이유를 돌려줘 에이전트가 고쳐 다시 보낸다.
- 그래프 편집 — 노드 추가, 드래그, 그룹 크기 조절, 연결·연결 설명 편집, 삭제, 확대·축소.
- 자동 정렬 — 왼쪽 위 도구의 「자동 정렬」이 연결 순서대로 왼쪽→오른쪽 층을 나눠 겹침 없이 촘촘하게 다시 배치한다. 교차가 적은 순서를 고르고, 단계는 앞뒤 단계의 가운데에 맞추며(분기는 출력 순서대로), 열 너비는 그 열의 가장 넓은 카드만큼만 쓴다. 긴 흐름은 화면 비율에 맞게 여러 줄로 접고, 서로 이어지지 않은 덩어리는 위아래로, 홀로 있는 노드는 아래에 줄지어 놓는다. 프로젝트·워크트리 그룹과 메모 그룹은 안부터 배치한 뒤 내용에 맞게 크기를 줄여 한 덩어리로 놓는다. 정렬 직후에는 「정렬 되돌리기」로 이전 위치로 돌아갈 수 있다(노드를 옮기면 사라짐). 자연어 생성·Task로 그래프 만들기·`PUT /api/workflows/:id?layout=auto` 도 같은 배치를 쓴다.
- 문서 저장 — JSON 파일로 로컬 저장·불러오기·가져오기·내보내기.
- Orca 연결 — Run 선택, Task와 의존 관계 자동 배치, 개별 노드의 Task 연결.
- 상태 표시 — 대기·실행 중·확인 필요·완료·실패·상태 미확인·미연결 구분, 병렬 작업 동시 표시.
- 전체 실행 — 상단·사이드바의 「전체 실행」에서 워크플로마다 카드·그래프 하나로 진행 중인 실행을 합쳐 보며(`?view=executions`로 바로 열기), 각 노드에 실행 중·확인 필요 등의 건수를 표시한다. 기본은 현재 단계 주변이고 「전체 단계 보기」로 펼칠 수 있으며, 상태 필터·워크플로/단계/태그 검색·10초 간격 갱신·완료 실행 제외·원래 캔버스의 모아 보기로 이동을 제공한다; 통합 화면을 열었다 돌아와도 편집 중인 내용은 유지된다.
- 실행 기록 — 한 그래프를 여러 번 실행한 기록을 `executions`로 저장한다. 실행 요청마다 Run이 따로 생기고 실행마다 자기 Run을 기억하므로, 여러 요청의 실행을 한 캔버스에서 함께 관찰한다. 실행 시 입력이 있는 요청의 실행 칩에는 그 입력(예: 티켓 키)이 붙는다. 모아 보기(노드별 실행 칩)와 실행 선택(실행 하나의 상태)을 전환하고, 끝난 실행은 항상 숨긴다.
- 실행 로그 — 상단 `실행 로그`에서 실행 요청별 기록을 본다. 진행 중·완료·실패를 가리지 않고 모두 남으며, 실행별·단계별 최종 결과 표를 보여 준다. 서버가 열린 Run을 10초마다 직접 관찰하므로 캔버스를 닫아 두어도 완료가 기록된다. 요청·브리프·코디네이터 기동·실행 등록·Task 상태 변화·코디네이터의 판단(워커 보고·게이트·오류·마무리 보고)을 시각순으로 보여 주고, 브리프·워커 산출물·보고 파일을 연다.
- 실행 중 가시성 — 지금 실행 중인 단계는 카드가 맥동하고 위에 「실행 중」 배지(여러 실행이면 `×n`)가 붙는다. 모아 보기에서 다른 실행의 실패·확인 필요가 노드 상태를 대표해도 실행 중이면 같이 표시한다. 확인 필요 단계는 노란빛으로 맥동하고, 미니맵에도 실행 중 단계가 깜박인다. 캔버스 왼쪽 아래 실행 중 바에 실행 중·확인 필요 단계가 나열되어 누르면 그 단계로 이동해 선택하고, 상단 「실행 중 n」이나 바 제목을 누르면 실행 중 단계를 차례로 돈다. 실행 중 카드는 청록 바탕과 테두리로 채워지고, 화면을 축소해도 테두리·배지가 화면에서 같은 크기로 남는다. 카드 글자를 읽기 어려울 만큼 축소하면(60% 미만) 실행 중·확인 필요·실패가 아닌 단계는 흐려진다. 사이드바의 현재 워크플로 옆에도 실행 중 단계 수가 뜬다.
- 1차 연관 — 단계 하나를 선택하면 연결 하나로 바로 이어진 앞 단계·다음 단계만 밝게 남고(카드에 「← 앞 단계」·「다음 단계 →」 표시) 나머지 단계와 연결은 흐려진다. 선택한 단계의 연결은 굵게 강조한다. 단계 속성의 「연결된 단계」에서 앞·다음 단계와 상태를 보고 눌러 그 단계로 이동한다. 빈 곳을 누르거나 여러 개를 선택하면 해제된다.
- 요약 보기 — 왼쪽 위 도구의 계기판 버튼이나 `S` 로 켜고 끈다(브라우저마다 기억). 단계 카드는 크게 쓴 제목, 상태(카드 색과 큰 상태 글자), 보이는 실행이 상태별로 몇 건인지(예: `실행 6 · 실행 중 3 · 대기 3`)만 남기고 지침·모델·소속은 감춘다. 아무 일도 없는 단계(대기·미연결·건너뜀)와 메모는 흐려진다. 캔버스 왼쪽에 「실행 현황」 패널이 떠서 진행 중인 실행마다 상태, 끝난 단계 수/전체(완료·건너뜀), 상태별 진행 막대, 실행 중·확인 필요·실패 단계 이름을 보여 준다. 줄을 누르면 그 실행만 보고, 다시 누르면 모아 보기로 돌아간다.
- 실행 화면 — 실행 중·확인 필요·미확인 노드나 칩을 클릭하면 해당 Task 최신 시도의 워커 터미널을 Orca에서 연다.
- 조회 장애 — 마지막 완료 표시를 재사용하지 않고 상태 미확인으로 전환.
- 실행 — `실행` 버튼(×횟수)이 그래프와 횟수를 담은 브리프로 Orca 코디네이터 에이전트(Claude Opus)를 띄운다. 코디네이터가 Run·Task 생성, 워커 기동, 자연어 조건 판단, 정리를 맡고 실행 목록을 캔버스에 등록한다. 실행 시 입력(워크트리 이름)과 설정값이 모두 같은 실행이 진행 중이거나 그런 직전 요청 뒤 60초 안이면 거부한다. 입력이나 설정값이 다르면 동시에 진행한다 — 예를 들어 티켓 키를 입력으로 받는 워크플로는 티켓마다 따로 실행해 병렬로 돌릴 수 있고, 다른 워크플로의 워커가 `POST /api/workflows/:id/execute` 로 티켓마다 실행을 요청할 수도 있다.
- 설정값 — 워크플로마다 환경변수 같은 설정값(키·이름·설명·기본값·필수)을 둔다. 아무것도 선택하지 않았을 때 오른쪽 패널에서 편집한다. 실행 창에서 값을 입력받고, 자동화는 입력한 값을 고정해 매번 쓴다. 단계 지침에 `{{키}}` 로 쓰면 브리프를 만들 때 값으로 바뀌고, 코디네이터 브리프에도 값 목록이 들어간다. 펼치는 링크와 「항목마다 따로 실행」 링크는 같은 키를 선언한 대상 워크플로에 값을 넘긴다. 선언하지 않은 `{{키}}` 가 지침에 있거나 필수 값이 비면 실행 전에 거부한다. 값은 워크플로 파일과 브리프에 그대로 남으므로 비밀값은 넣지 않는다.
- 실행 창 — 실행 버튼은 항상 창을 띄워 실행할 프로젝트(Orca에 열린 프로젝트), 병렬 횟수, 실행 시 입력 워크트리 이름, 설정값, 완료 시 정리(워커 세션 정리·만든 워크트리 삭제·코디네이터 종료)를 받는다. 코디네이터 종료를 고르면 실패한 단계나 남은 확인이 있어도 마무리 보고 뒤 닫는다(남은 것은 보고와 실행 로그에 남는다). 워커가 worker_done 없이 터미널째 사라지면 코디네이터는 기다리지 않고 그 단계를 실패로 닫는다. 그룹 밖 단계와 프로젝트를 정하지 않은 새 워크트리는 고른 프로젝트를 쓰고, 코디네이터도 거기서 시작한다. 비워 둔 입력은 실행 중에 코디네이터가 묻는다.
- 자동화 — 실행 창에서 「자동화로 예약」을 고르면 그 설정을 고정한 Orca 자동화(`orca automations`)를 만든다. 예약 시각에 Orca가 띄운 에이전트가 캔버스에서 브리프를 받아 코디네이터가 되므로 그때 캔버스 서버가 떠 있어야 한다. 사이드바에서 일정·다음/마지막 실행을 보고 지금 실행·삭제하며, 자동화가 시작한 실행은 실행 칩과 캔버스 상단에 자동화 이름을 표시한다.
- 작업 위치 — 단계가 든 가장 안쪽 워크트리 그룹, 없으면 프로젝트 그룹, 그것도 없으면 실행 때 고른 프로젝트다.
- 코디네이터 위치 — 기본은 실행 때 고른 프로젝트다. 아무것도 선택하지 않았을 때 오른쪽 패널의 「코디네이터 위치」에서 워크트리 그룹을 고르면, 서버가 실행 요청을 받은 뒤 그 워크트리를 찾거나(같은 이름·브랜치면 그대로 재사용) 「부모 워크트리」 아래 새로 만들고 코디네이터를 그 안에서 띄운다. 준비와 기동 결과는 실행 로그에 남는다. 그룹 이름은 직접 지정이나 실행 시 입력이어야 하고, 「실행마다 따로 만들기」는 쓸 수 없으며, 실행 중에 만들어질 워크트리 안에 둘 수 없다. 자동화가 띄운 코디네이터(자동화 에이전트 자신)는 실행 프로젝트에서 시작하므로 이 설정은 실행 버튼과 「항목마다 따로 실행」 링크가 띄우는 실행에 적용된다.
- 워크플로 링크 — 실행 시 링크 대상의 단계를 펼쳐 Task로 만들고, 링크 노드는 펼친 Task 상태를 모아 보여준다. 「실행 방식」을 「끝날 때까지 대기」(기본)로 두면 링크 뒤 단계가 펼친 단계를 모두 기다리고, 「시작만 하고 진행」으로 두면 링크 앞 단계만 기다려 펼친 단계와 동시에 진행한다(실행은 펼친 단계까지 끝나야 끝난다). 「항목마다 따로 실행」으로 두면 펼치지 않고, 앞에 연결한 워커 하나가 `items: a, b` 로 보고한 항목마다 대상 워크플로를 별도 실행으로 요청한다 — 항목은 대상의 「실행 시 입력」 워크트리 이름이 되므로 대상에 그런 그룹이 정확히 하나 있어야 하고, 한 번에 20개까지, 같은 실행에서 이미 요청한 항목은 다시 띄우지 않는다. 요청이 끝나면 링크는 완료이고 따로 띄운 실행은 기다리지 않는다. 링크 노드에 요청한 항목이 칩으로 보이고, 속성에서 항목을 누르면 대상 워크플로를 연다. 대상 미지정·없는 워크플로·순환·3단계 초과 중첩은 실행 전에 거부한다. 단계가 든 그룹에 대상(또는 생성할 프로젝트)이 없어도 거부한다.
- 실행 경계 — 캔버스 서버는 워커를 직접 띄우거나 멈추지 않는다. 워크트리는 코디네이터가 준비하고, 서버는 「코디네이터 위치」로 고른 워크트리 하나만 코디네이터를 띄우기 전에 준비한다. 워커 실행·중지, 질문 응답, 승인, 의존성 실행은 코디네이터가 담당한다. 사용자 개입 게이트는 「묻지 않음 (자동 승인)」으로 둔 것 말고는 자동 승인하지 않고 결정 게이트로 사용자에게 묻는다. 서버가 하는 일의 예외는 하나 더 있다 — 「코디네이터 종료」를 고른 실행이 끝났는데 코디네이터 터미널이 남아 있으면(보고 1분 뒤, 보고가 없으면 10분 뒤) 서버가 닫는다.
- 삭제 — 왼쪽 목록이나 상단의 휴지통으로 저장 파일을 지운다. Orca의 Run·Task는 남는다.
- 연결과 분기 — 일반 연결은 모두 병렬이다. 한 단계에 여러 연결이 들어오면 기본은 「모두 필요」로, 앞 경로 하나라도 건너뛰어지면 그 단계도 건너뛴다. 분기에서 갈라진 경로가 다시 모이는 단계는 합류 방식을 「하나라도 오면 진행」으로 둔다. 어느 쪽이든 진행 중인 앞 단계가 모두 끝난 뒤 시작한다.
  - 골라서 진행할 때만 분기 노드를 쓴다. 출력마다 조건과 연결 포트가 있고, `하나만`(배타) 또는 `해당하는 것 모두`(포함)를 고른다.
  - 판정 주체 — 직전 단계 워커(worker_done 첫 줄 `decision:`), 판정 전용 워커, 사용자 중 하나. 코디네이터는 판정하지 않고 결과를 캔버스에 등록한다.
  - 사용자 결정 — 사용자 판정 분기와 게이트(통과·거절)는 앞 단계가 끝나면 캔버스 오른쪽 위 「결정 대기」 카드에 뜬다. 코디네이터는 결정 게이트만 걸고 기다리지 않으며, 30초마다 캔버스에 등록된 판정을 가져가 반영한다. 여러 실행·단계의 결정이 서로 다른 시점에 생겨도 서로 막지 않는다. 코디네이터 터미널에 직접 답해도 된다.
  - 게이트 거절 — 그 뒤 단계는 합류 방식과 관계없이 건너뛴다.
  - 자동 승인 — 게이트의 「묻는 곳」을 「묻지 않음 (자동 승인)」으로 두면 결정 대기 카드에 뜨지 않고, 앞 단계가 끝나면 코디네이터가 통과로 등록한 뒤 실행 로그에 「자동 승인」을 남긴다. 다시 묻게 하려면 묻는 곳만 바꾼다.
  - 워커에서 묻기 — 게이트의 「묻는 곳」을 「직전 단계 워커의 터미널」로 두면, 앞에 연결된 워커 하나가 작업을 마친 뒤 worker_done 전에 자기 터미널에서 사용자에게 묻는다. 작업 맥락을 가진 워커에게 되묻거나 고쳐 달라고 할 수 있고, 답에 따라 `decision: approve|reject` 로 보고한다. 그 워커가 입력을 기다리는 동안 결정 대기 카드에도 「워커 열기」와 함께 뜨며, 카드에서 먼저 고르면 코디네이터가 워커에게 알려 마무리시킨다. 게이트 앞에 워커가 하나가 아니면 실행 전에 거부한다.
  - 고르지 않은 출력 뒤 단계는 캔버스가 계산해 건너뜀으로 표시한다. 분기 연결은 노란 점선, 실행을 고르면 고른 출력은 밝게, 고르지 않은 쪽은 흐리게 보인다.
  - 되돌아가기 — 반복(보완 후 재검토 등)은 「하나만」 분기의 출력에서 그 분기로 이어지는 앞 단계로 연결해 만든다. 앞 단계로 연결하면 캔버스가 되돌아가기 연결(보라색 점선, 최대 3회)로 만들고, 연결 속성에서 최대 반복 횟수(1~200)와 「반복을 다 쓰면」 갈 출력을 정한다. 그 출력을 고르면 대상부터 분기까지를 새 회차로 다시 돈다 — 코디네이터가 새 Task 를 만들고, 앞 회차 기록은 실행의 `history` 에 남으며, 노드에 「n회차」가 붙는다. 회차 n 은 그 단계가 실행에서 몇 번째로 도는지(단계 기준 누적)이고, 최대 반복은 연결마다 센다(아래 「런타임 계약」). 횟수를 다 쓴 뒤 또 고르면 정해 둔 출력으로 바뀐다. 반복 출력에는 그 연결 하나만 두고, 반복 구간에 워크플로 링크를 둘 수 없으며, 되돌아가기가 있는 워크플로는 펼치는 링크의 대상이 될 수 없다(「항목마다 따로 실행」은 된다).
  - 되돌아가기가 아닌 연결은 순환할 수 없다(저장 시 거부). 연결 설명은 참고 정보이며 진행 여부를 바꾸지 않는다.
- 예시 워크플로 — `examples/` 의 JSON 을 서버 기동 때 저장 위치로 한 번씩 복사한다. 같은 ID 의 문서가 있으면 덮어쓰지 않고, 한 번 넣은 예시는 지우거나 고쳐도 다시 넣지 않는다(기록: 저장 위치의 `.examples.json`). 예시 중 QA 티켓 흐름은 두 개다 — 「QA 티켓 선별」(에픽의 신규·재오픈 하위 티켓을 claim 하고 티켓마다 해결 실행을 요청)과 「QA 티켓 해결」(티켓 워크트리에서 분석 → 구현 방향(자동 승인) → 구현 → 검토 → 화면 실측 → 반출 승인 → 반출 → 머지 지시 → 머지). 워크트리 정리는 해결 실행 안에서 하지 않는다 — 그 안에서 지우면 정리하는 워커와 그 워크트리의 코디네이터 터미널이 함께 닫혀 실행이 끝나지 않는다. 선별 플로의 「끝난 티켓 정리」가 회차마다 티켓 워크트리 밖에서 `qa-driver sweep` 으로 해결 실행이 끝난 티켓만 지운다(qa-ticket-driver 의 `run` 회차 정리와 같다). 반출 승인·머지 지시는 캔버스 카드나 QA 대시보드(`qa-driver approve`·`merge` 가 게이트에 넣는다)에서 고르고, 게이트가 열리기 전에 먼저 골라도 코디네이터가 그 판정을 쓴다. 두 예시는 `qa-ticket-driver` 스킬의 상태 디렉터리와 스크립트를 쓰므로 그 스킬이 설치되어 있어야 그대로 돈다. 「워크플로 검증」은 저장된 워크플로 하나(설정값 「검증할 워크플로 ID」)를 검증한다 — 실행 전 검사(`GET /api/workflows/:id/check`) → 판정·보고 계약, 지침 실행 가능성, 흐름·병렬성 세 갈래 검토(병렬) → 취합·판정 → 사용자가 고르면 수정안을 대상에 저장하고 처음부터 재검증(최대 2회) → 통과했고 「시범 실행 요청」이 있으면 사용자가 고를 때 실제로 한 번 실행해 관찰 → 검증 보고. 실행 프로젝트로 workflow-canvas 체크아웃을 고른다.
- 이전 문서 — 저장 형식의 `task` 노드는 읽을 때 `worker` 로 바뀐다.
- 호환 범위 — 자체 v1 JSON 형식이며 CC Workflow Studio 파일의 직접 가져오기는 지원하지 않는다.

## 런타임 계약 (그래프 작성용)

그래프 지침이 전제로 삼는 캔버스·코디네이터 동작이다. 생성 프롬프트(`server/generate.ts`)도 같은 목록(`server/contract.ts` 의 `runtimeContract`)을 쓰고, 테스트가 이 절과 상수가 같은지 확인한다.

<!-- runtime-contract:start -->
- **빈 설정값** — 선언했지만 실행 때 비운 설정값은 지침의 `{{키}}` 자리에 빈 문자열로 들어간다. 「`{{키}}` 가 중괄호 그대로면」으로 판별하지 말고 「값이 비어 있으면」으로 쓴다.
- **설정값이 닿는 곳** — 설정값은 단계 지침·스크립트 명령·부모 워크트리 경로에 `{{키}}` 로 쓴 곳에만 들어간다. 선언만 하고 어느 지침에도 쓰지 않으면 워커는 그 값을 모른다. 분기 출력 이름·게이트 질문에는 치환하지 않는다.
- **판정** — 분기·게이트 판정은 워커의 worker_done **첫 줄** `decision: <출력 id>[,<출력 id>...]` 만 인정한다. 없거나 출력 목록에 없는 값이면 코디네이터는 추측하지 않고 사용자 결정(캔버스 결정 카드)으로 넘긴다. 같은 분기는 한 번만 판정한다(재실행해 고르지 않는다).
- **반복 소진** — 되돌아가기 연결은 연결마다 최대 반복(1~200)을 센다. 다 쓴 뒤 그 출력을 고르면 판정이 연결의 「반복을 다 쓰면」(exit) 출력으로 바뀌어 기록되고 워커에게는 따로 알리지 않는다 — exit 출력 뒤 단계는 반복 소진으로 온 경우도 처리해야 한다.
- **회차 번호** — 되돌아가기로 다시 도는 단계의 산출물은 `<n>-<노드 id>-r<k>.txt` 이고, k 는 그 단계가 이 실행에서 몇 번째로 도는지다(단계 기준 누적, 2부터. 같은 단계로 가는 루프가 여럿이어도 합쳐 센다. 1회차는 `-r` 없이 `<n>-<노드 id>.txt`). 그래서 그 단계의 앞 회차는 언제나 `-r<k-1>` 이다. 「가장 최근 회차」는 이름 사전순이 아니라 k 를 숫자로 비교한 최댓값(또는 `ls -t` 맨 위)으로 고르고, glob 에는 노드 id 를 정확히 적어 `-children`·`-result` 같은 다른 파일이 섞이지 않게 한다. 최대 반복은 회차와 따로 연결마다 센다.
- **죽은 하위 실행** — 실행 로그 outcome(`GET /api/workflows/<id>/logs`)은 pending·running·blocked·completed·failed·unknown·stalled 다. `stalled` 는 코디네이터 터미널이 Orca 에서 사라졌는데 `finished` 이벤트가 없는 실행이다(Orca 가 응답하지 않을 때는 stalled 로 보지 않는다). 하위 실행을 기다리는 그래프는 `stalled` 를 `failed` 와 같이 「끝났지만 성공 아님」으로 다루고 더 기다리지 않는다.
- **사용자 분기 판정 전달** — 코디네이터는 워커 spec 마다, 이 실행에서 그 워커보다 앞서 내려진 사용자(judge `user`) 분기 판정을 `## 앞 사용자 분기 판정` 절로 전한다. 절의 줄은 `- <분기 노드 id> (<라벨>): <출력 id>` 이다. Task 는 판정 전에 만들어지므로 spec 의 이 절은 코디네이터가 워커를 띄우기 직전에 쓰는 `<n>-<노드 id>-user-decisions.md` 를 가리킨다. 판정이 없으면 그 파일이 없다(그래프에 사용자 판정 분기가 없으면 절도 없다). 게이트(통과·거절)는 들어가지 않는다.
- **모델별 병렬 워커 전원 실패** — fanout 단계의 모델 워커가 모두 실패해도 단계와 실행을 실패로 끝내지 않는다. 코디네이터는 결과 줄 `모델별 <완료 k>/<전체 m> · 실패 <name>(<사유>), ... · 산출물 <경로, ...>` 을 단계 Task 결과와 단계 산출물 `<n>-<노드 id>.txt`(2회차 이상 `-r<k>.txt`)에 남기고 다음 단계로 진행한다. 뒤 단계가 결과 줄로 전원 실패(`모델별 0/<m>`)를 판단한다.
- **코디네이터 정리** — 단계 워커가 worker_done 에 `코디네이터 정리 필요: <터미널 핸들>[, <터미널 핸들> ...]` 한 줄을 적으면, 코디네이터가 그 단계가 끝난 직후(다음 단계를 띄우기 전에) 그 터미널을 닫는다. 코디네이터 자신과 이 Run 에서 아직 일하는 워커의 터미널은 닫지 않는다.
- **location 안 터미널 닫기 금지** — 워커는 자기 location 워크트리를 지우거나 그 안의 터미널을 닫지 않는다(자기 터미널이 함께 닫혀 worker_done 을 보낼 수 없다). 그런 정리가 필요하면 위 「코디네이터 정리」 줄로 보고한다.
- **문서 저장** — `PUT /api/workflows/:id` 는 런타임 쓰기와 같은 직렬 큐에 들어가고, 본문의 `executions`·`automations` 는 무시하고 서버의 현재 값을 보존한다. `GET` 응답의 `ETag`(문서 버전)를 `If-Match` 로 보내면 그 사이 문서가 바뀌었을 때 409 와 현재 `version` 을 돌려준다.

## 설치와 기동

- 요구 사항 — Node.js 22 이상, npm, 실행 중인 Orca 앱과 버전에 맞는 Orca CLI.
- 설치·빌드·실행:

```sh
npm ci
npm run build
./bin/workflow-canvas
```

- 기본 주소 — `http://127.0.0.1:4318`. Orca 프로젝트의 브라우저 탭에서 연다.
- tailnet — 서버는 127.0.0.1 에만 묶이고, 다른 기기에서는 `tailscale serve --bg --https=4318 http://127.0.0.1:4318` 의 https 주소로 연다. API 는 루프백과 `*.ts.net` 호스트만 받고, 코디네이터·워커에게 주는 콜백 주소는 요청이 어디로 왔든 `http://127.0.0.1:<포트>` 다. 에이전트 대시보드의 「워크플로 캔버스」 탭이 이 주소를 메트릭 서버에서 받아 iframe 으로 띄운다.
- 개발 — `npm run dev`로 같은 주소에서 개발 서버를 실행한다.
- 포트 변경 — `./bin/workflow-canvas --port 4320`.
- CLI 선택 — `ORCA_CLI_COMMAND` 우선, 개발 환경은 `orca-dev`, Linux 외부 터미널은 `orca-ide`, 그 외는 `orca`.
- 환경 변수 — `WORKFLOW_CANVAS_PORT`, `WORKFLOW_CANVAS_DATA_DIR`, `ORCA_CLI_COMMAND`.
- 저장 위치 — 기본 `<checkout>/.local/workflows/`. 로컬 데이터·캐시·빌드 결과는 git에서 제외한다.
- 저장 데이터 — Task 지침·Run/Task ID가 들어갈 수 있으므로 실제 연결 데이터는 공개 저장소에 추가하지 않는다.

## 사용

1. 노드를 선택해 이름·지침을 편집하고 포트를 연결한다.
2. 왼쪽에서 Orca Run을 선택한다.
3. `Task로 그래프 만들기`로 의존 관계를 가져오거나, 단계 속성에서 기존 노드에 Task를 연결한다.
4. 3초 간격으로 갱신되는 상태를 확인한다.
5. `저장`으로 로컬에 보관한다. 문서 이동 시 JSON 내보내기·가져오기를 사용한다.

## 공개 면

- `bin/workflow-canvas` — 로컬 서버 실행 진입점.
- `exports/workflow.schema.json` — 저장·교환용 JSON Schema. 고유 노드·연결 ID와 참조 무결성도 서버에서 검사한다.
- `examples/` — 기동 때 저장 위치에 넣는 예시 워크플로(저장 형식 그대로, 실행 기록·Run ID 없음).
- 저장소 내부 코드 — 외부 도구에서 `src/`·`server/`를 직접 참조하지 않는다.
- 설계와 API — [[40_Tools/workflow-canvas/docs/설계와 연동|설계와 연동]].
