> 그래프 설계 문서와 Orca의 실행 상태를 연결하는 구조다. 실행의 원본은 Orca이며 캔버스는 편집과 관찰을 담당한다.

## 구성

- 화면 — React·TypeScript·React Flow, 편집 상태와 관찰 상태를 분리한다.
- 서버 — Express·TypeScript, 루프백 주소에서만 수신한다.
- 개발 — Vite 미들웨어를 서버에 연결해 API와 화면을 같은 출처로 제공한다.
- 저장 — v1 JSON의 노드(그룹 노드의 대상·경로·크기, 메모 그룹(`type`·`kind` `frame`)의 위치·크기, 일반 노드의 종류·링크 대상·모델(`workerModel`)·추론 수준(`effort`), 그룹 소속)·연결·Run/Task 바인딩(링크 노드는 `executions[].links`)을 저장하며 실행 상태는 저장하지 않는다.
- 쓰기 — 선택된 로컬 데이터 디렉터리에 원자적으로 저장한다.
- 단독 실행 — 볼트의 문서·스킬·등록부를 읽지 않는다.

## Orca 조회

| 목적 | CLI 공개 면 |
| --- | --- |
| 연결 상태 | `orca status --json` |
| Run 목록 | `orca orchestration run-list --json` |
| Run 정보 | `orca orchestration run-show --id <run-id> --json` |
| Task 상태·의존 관계 | `orca orchestration task-list --run <run-id> --json` |
| 워커 관측 | `orca orchestration worker-list --run <run-id> --include-remote --json` |
| 실행 화면 열기 | `orca terminal switch --terminal <handle> --json` |
| 코디네이터 기동 | `orca agent launch --agent claude --model claude-opus-5-5 --surface terminal --worktree path:<checkout> --prompt <brief> --json` |
| 코디네이터 탭 이름 | `orca terminal rename --terminal <handle> --title <text> --json` |

- 페이지 — Run과 Worker 응답의 다음 커서를 따라 조회한다.
- 호출 — 고정 명령과 검증된 Run ID를 인수 배열로 전달한다. 셸 명령 문자열을 실행하지 않는다.
- 관찰 — 수신함을 소비하거나 완료 메시지를 승인하지 않는다.
- 범위 — 접속된 Orca 호스트의 Run 목록이며 작업 폴더별로 자동 필터링하지 않는다.
- 조회 주기 — 연결·목록은 15초, 선택한 Run의 스냅숏은 3초 간격. 이전 조회가 끝난 뒤 다음 조회를 예약한다.

## 상태 판정

- 완료·실패 — Task의 명시적 상태를 우선한다. 살아 있는 터미널이 완료 Task를 실행 중으로 바꾸지 않는다.
- 실행 중 — Task가 진행 상태이고 최신 워커 관측이 끊기거나 종료되지 않은 경우다.
- 미확인 — CLI 조회 실패, 알 수 없는 상태, Task 부재, 최신 워커의 `unverifiable`·`exited` 관측.
- 확인 필요 — Task가 차단·입력 대기 상태이거나 최신 워커가 해당 활동을 보고하는 경우다.
- 미연결 — 노드에 Task ID가 없다.
- 재시도 — `worker-list`의 최신 시도 우선 순서를 사용한다. 과거 워커의 생존으로 최신 시도를 대체하지 않는다.
- 건너뜀 — 분기 판정(`executions[].decisions`)으로 서버가 계산한 `executions[].skipped` 의 단계다. 코디네이터가 합류 단계의 deps 를 풀려고 그 Task 를 완료로 닫아도 캔버스는 건너뜀으로 표시한다.
- 건너뜀 계산 — 위상 순서로 훑는다. 죽은 연결은 출발 단계가 건너뜀이거나, 판정이 끝난 분기의 고르지 않은 출력에서 나온 연결이다. 판정 전 분기의 출력은 살아 있다. 합류 방식이 `all`(기본)이면 죽은 연결이 하나라도 있으면, `any` 면 모두 죽었을 때 건너뛴다. 거절된 게이트 뒤 단계는 합류 방식과 관계없이 건너뛴다.
- 끝난 실행 — 모든 단계가 완료 또는 건너뜀이고 완료가 하나 이상일 때다. 대기 단계가 남아 있으면 진행 중이다.
- 결정 대기 — 사용자 판정 분기와 게이트 중, 판정이 없고 건너뛰지 않았으며 앞 단계(건너뜀 포함)가 모두 완료된 것. 직전 워커가 묻는 게이트(`asker: previous`, 흐름에서는 judge `previous`)는 그 워커의 Task 가 확인 필요(입력 대기)일 때 뜬다. 캔버스가 Run 스냅숏과 `GET /api/workflows/:id/flow` 로 계산해 카드로 보여준다.
- 선택 변경 — Run을 바꾸면 기존 Task 연결을 지워 다른 Run의 상태를 혼용하지 않는다.

## 로컬 API

| 요청 | 결과 |
| --- | --- |
| `GET /api/status` | 연결 여부·앱 버전 |
| `GET /api/runs` | Run 목록 |
| `GET /api/runs/:id` | Task·Worker 정규화 스냅숏 |
| `POST /api/runs/:id/tasks/:taskId/open` | Task 최신 시도의 워커 터미널을 Orca 화면에 띄움 |
| `POST /api/workflows/:id/execute` | `{count, project, inputs?, cleanup?}`(count 1~20)로 코디네이터 기동. 같은 `inputs` 의 실행이 진행 중이거나 60초 안에 같은 입력으로 요청했으면 409, 입력이 다르면 동시에 기동한다. 브리프는 `<data>/.executions/<시각>-<id>/brief.md` |
| `PUT /api/workflows/:id/executions` | 코디네이터 전용. `{runId, launch, executions}` — 그 Run 의 실행만 교체하고 다른 Run 의 실행은 남긴다(최대 100개, 오래된 것부터 버림). 실행마다 `runId` 와 요청의 실행 시 입력(`inputs`)을 붙이고, 입력이 있으면 라벨 앞에 붙인다. 실행 id 는 `<run_id>-<n>` 이며 다른 Run 이 쓰는 id 면 400. 같은 Run 재등록은 기록된 판정을 유지 |
| `POST /api/workflows/:id/executions/:executionId/decisions` | 코디네이터·결정 대기 카드. `{node, outputs, by?}` 분기·게이트 판정을 검증·기록하고 `{decisions, skipped, skippedTasks}` 반환. 다른 출력으로 바꾸려 하면 409. `by: user` 는 실행 로그에 남긴다 |
| `GET /api/workflows/:id/executions/:executionId/decisions` | 코디네이터가 기다리는 동안 가져가는 판정과 닫을 Task |
| `GET /api/workflows/:id/flow` | 링크를 펼친 실행 그래프(결정 대기 계산용) |
| `POST /api/generations` | `{kind: workflow|brief, prompt, project, workflow?, nodeId?}`. Orca에 열린 프로젝트에서 생성 에이전트를 `orca agent launch` 로 띄우고 `{id, status}` 반환. 프롬프트는 `<data>/.generations/<id>/prompt.md` |
| `PUT /api/generations/:id` | 생성 에이전트 전용. 워크플로 `{name, description, nodes, edges}`(배치·검증 후 새 문서로 저장) 또는 지침 `{description, label?}`, 포기하면 `{error}`. 틀리면 400 과 이유 |
| `GET /api/generations/:id` | 생성 상태(`pending`·`done`·`failed`)와 결과. 서버 메모리에만 있고 30분 지나도 결과가 없으면 실패 |
| `DELETE /api/workflows/:id` | 저장 파일 삭제 |
| `GET /api/workflows` | 저장된 그래프 목록(최근 저장순) |
| `GET /api/workflows/:id` | 그래프 문서 |
| `PUT /api/workflows/:id` | 검증·저장 |
| `POST /api/validate` | 가져올 문서 검증, 저장 없음 |
| `GET /api/workflows/:id/logs` | 실행 로그 목록(실행 요청별, 최근 50개) |
| `GET /api/workflows/:id/logs/:logId` | 실행 로그 상세: 메타·이벤트·파일 목록 |
| `GET /api/workflows/:id/logs/:logId/files/:name` | 로그 폴더의 파일 내용(브리프·워커 산출물·보고, 앞 1MB) |
| `POST /api/workflows/:id/logs/:logId/events` | 코디네이터 전용. `{type, message, taskId?}` 로 판단 기록. type 은 `note`·`gate`·`worker`·`error`·`report` |

- 출처 — 루프백 Host와 같은 Origin만 허용한다.
- 오류 — 하위 프로세스의 원시 stdout·stderr를 API에 노출하지 않는다.
- 경로 — API가 임의 파일 경로·CLI 명령을 받지 않는다.
- 화면 열기 — 터미널 핸들은 서버가 Run 스냅숏에서 찾는다. 클라이언트는 Run·Task ID만 보내며, 정리된 워커와 과거 시도는 열지 않는다. 입력 전송·수명 주기 변경은 하지 않는다.
- 한계 — 루프백 API는 동일 머신 사용자 경계를 제공하지 않으므로 공유 호스트의 공개 서비스로 사용하지 않는다.

## 실행 로그

- 단위 — 실행 요청 하나(실행 버튼 또는 자동화 발화)가 로그 하나다. 폴더는 `<data>/.executions/<시각>-<id>/` 이고 `meta.json`(워크플로·시작 시각·횟수·프로젝트·자동화·Run ID)과 `events.jsonl` 을 둔다. 브리프·워커 산출물·`report.md` 도 같은 폴더에 남는다.
- 서버 기록 — 실행 요청, 브리프 작성, 코디네이터 기동·기동 실패, 실행 등록(`PUT executions` 때 Run ID를 `launch` 가 가리키는 로그에 묶는다. `launch` 가 없으면 그 Run 을 이미 가진 로그, 그다음 가장 최근 미등록 로그).
- 상태 변화 — 서버가 등록된 Run 중 끝나지 않은 것을 10초마다 직접 조회한다(캔버스가 닫혀 있어도 기록된다). `GET /api/runs/:id` 조회와 로그 상세 조회도 관찰을 겸한다. Task 상태가 바뀌면(캔버스 상태 판정 기준) 한 줄씩 남긴다. 같은 Run의 관찰은 직렬화해 중복을 막고, 재시작 뒤에는 기존 이벤트에서 마지막 상태를 복원한다. 시작한 지 7일이 지난 실행은 배경 조회를 멈춘다.
- 완료 기록 — 실행마다 끝나거나(완료) 실패·확인 필요가 되면 `execution` 이벤트에 단계별 결과를 남기고, 모든 실행이 완료 또는 실패로 정리되면 `finished` 이벤트를 남긴다. 끝난 실행에서 대기로 남은 단계는 '진행 안 함'(선택되지 않은 분기)으로 표시한다. 실행 등록 때 실행별 Task ID를 `meta.json` 에 함께 저장하므로, 나중 실행이 워크플로의 실행 목록을 바꿔도 이전 실행의 결과를 볼 수 있다.
- 이전 실행 — 실행 로그 도입 전 폴더(`meta.json` 없음)는 워크플로가 지금 가리키는 Run을 가장 최근 폴더에 연결한다(`adopted`). 이 경우 이벤트 시각은 관찰 시각이다. 연결할 Run이 없는 폴더는 `Run 미확인`으로 남고 파일만 볼 수 있다.
- 코디네이터 기록 — 브리프가 로그 주소를 알려 주고, 워커 보고 처리·게이트·오류·마무리 보고 때 판단과 근거를 남기게 한다.
- 화면 — 상단 `실행 로그` 버튼. 실행 목록(결과 배지), Orca에서 읽은 실행별·단계별 결과 표, 이벤트 타임라인(Task 상태 변화 숨기기), 폴더 파일 열람. 4초마다 갱신한다. 끝난 실행은 캔버스에서 숨지만 로그에는 남는다.

## 확장 경계

- 실행 — 서버는 실행 엔진을 두지 않고 감독형 코디네이터 에이전트에 위임한다. 판정 수집(직전 워커·판정 워커·사용자)과 등록, 터미널 재사용, 릴리스, 복구는 코디네이터 책임이다. 진행 규칙(병렬·합류·건너뜀)은 캔버스가 정하고 코디네이터는 따른다. 서버는 중복 기동만 막는다(같은 실행 시 입력의 진행 중 실행 존재, 같은 입력 60초 간격). 캔버스는 문서의 Run 과 실행들의 Run 을 모두 관찰하고, 실행이 모두 끝난 Run 은 더 조회하지 않는다.
- 실행 판정 — 건너뛴 단계의 Task는 `completed --result skipped` 로 닫힌다. 기동 직후 아직 시작되지 않은 실행은 진행 중으로 본다.
- 실행 전 거부 — 출력이 두 개 미만인 분기, 조건이 빈 출력, 앞에 단계가 없는 분기, 앞에 워커 하나가 아닌데 직전 워커 판정인 분기.
- CC Workflow Studio — 현재 저장 형식이 다르므로 사용할 경우 변환기를 둔다.
- 상태 전송 — 현재는 주기 조회이며 WebSocket·이벤트 스트림은 제공하지 않는다.
- 화면 임베딩 — 로컬 URL을 Orca 브라우저에서 열어 사용한다. Orca 앱 내부 확장 등록 API는 사용하지 않는다.
